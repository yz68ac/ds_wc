# 不经桌面点击的图片下载：接口定位

日期：2026-10-26。样本固定为 Linux 微信 4.1.13.26 x86_64，主程序 SHA-256：

```text
2749535f299ba67feb8ef80cab898bb0531fa8f376b16f8a72db706811c84132
```

本轮完成静态调用链、参数传递、异步结果结构和运行时服务定位。**尚未在真实微信里调用这些下载函数，未证明它们已经可以取得清晰缓存，也未替换现有桌面兼容下载。** 本页所有函数名称都是研究标签，地址均为 RVA。

## 新发现：可以继续向下绕过上层等待

之前定位的 `0x70e7530` 负责获取可用图片。它会调用下载方法，再通过 `0x9aef560` 等待结果；这个等待步骤要求微信自己的协程上下文。仅把整个上层 getter 放进 GLib 主线程回调仍不够。

本轮沿该方法的实际调用点继续分析，定位到：

| RVA | 已核对的作用 | 验证状态 |
| --- | --- | --- |
| `0x6517cd0` | 从上层消息对象取得核心消息 shared_ptr，再转交下层下载 | 反编译及寄存器参数传递核对 |
| `0x6517dc0` | 接受核心消息 shared_ptr、资源规格、调用来源/优先级及选项，返回异步结果 | 已反编译；函数自身不调用上层协程等待 |
| `0x605f720` | 从上层消息 `+0x238/+0x240` 复制核心消息 shared_ptr 并增加引用计数 | 静态核对 |
| `0x6b49960` | 按会话字符串与消息 ID 查询消息的候选入口，返回异步结果 | 反编译、已有调用者核对；实际请求未运行 |
| `0x6541270` | 查询结果的带类型校验访问器 | 汇编确认返回结果指针；内部可能等待 |
| `0x6545070` | 下载结果的带类型校验访问器，正常调用者按返回整数状态判断成功 | 汇编确认返回结果指针；内部可能等待 |
| `0x9abce00` | 读取异步状态对象 `+0x84` 的状态值 | 只有一次字段读取，不是协程等待 |
| `0x9abe480` | 通用结果访问；未完成时等待条件变量，再取 `+0x78` 的类型擦除结果 | 已反编译；不能拿它在主线程轮询未完成任务 |

因此更合适的候选路线是：

```text
从全局账号上下文定位核心消息服务
  → 对指定群、原消息 ID 发起原生查询
  → 保留查询 future，观察就绪状态
  → 就绪后取得消息并核验来源
  → 取得核心消息 shared_ptr
  → 调用下层下载启动方法，保留下载 future
  → 观察就绪状态，完成后检查结果
  → 沿原消息绑定的缓存路径验收新增清晰图片
```

这条路线的参数来源和目标都不需要 ChatInputView、当前选中会话、AT-SPI 或鼠标坐标。它是否能够完整地在选定线程下运行，仍需要受控调用验证；不能仅凭“函数本身没有 wait”断言其全部下游都可随意调用。

## 运行时对象定位已通过只读核对

使用 `/proc/<pid>/mem` 的有界只读访问，先检查进程属主、可执行路径、整文件 hash 和候选函数指纹。没有 Frida attach、Hook、原生函数调用或数据库查询。

```text
base + 0xacf6710 → kernel
kernel + 0x68    → 当前 account
account + 0x28   → 核心服务上下文
  同步服务缓存：context + 0x00
  异步服务缓存：context + 0x28
```

该时刻同步缓存有 85 项，异步缓存为空。从静态描述符 `0xa8ab498` 的名称访问器推得类型标识，再在已有同步缓存中唯一匹配到消息服务：

| 位置 | 只读观察结果 |
| --- | --- |
| 核心消息服务对象 | 虚表 RVA `0xa8c4568` |
| 消息服务 `+0x950` | 查询对象存在，虚表 RVA `0xa8c4868` |
| 新启动服务、延迟创建或原生方法调用 | 0 次 |
| 微信桌面操作、下载请求 | 0 次 |

两个缓存不能混用：先前只看异步缓存会得到空表，并不表示核心消息服务不存在。服务类型标识为 32 字节不透明值，不将其解读成官方类名。

实现时必须每次重新核对进程、服务和对象；这里没有提供可跨重启保存的裸指针，也未修改引用计数来延长任何既有对象的生命。

## 调用形状与生命周期

根据已有调用点和 x86_64 参数寄存器，下层启动方法的研究原型可写为：

```text
start_image_task(
    result_shared_ptr_out,
    core_message_service,
    core_message_shared_ptr,
    resource_kind,
    request_origin_or_priority,
    options
)
```

前三项已能与调用链对应；两个整数和 options 的完整语义仍需继续还原。上层正常路径中出现过规格值 1、2，以及调用来源/优先级候选值 200、400 等，但**尚不能把这些数直接命名为缩略图、清晰图、原图或超时时间**。

共享状态的 `+0x84` 在当前实现中表现为 0 待定、1 有值、2 异常；`+0x78` 保存类型擦除结果。应先确认就绪和状态，再调用匹配的结果访问器；不能直接拿已返回的 future 指针当成图片对象或成功标志。

Ghidra 对两个结果访问器最初推导为 `void`，但汇编中的成功分支明确把结果指针放入 RAX 返回。直接按伪 C 声明封装会丢失结果或使用错误返回类型，这也是本轮额外核对汇编的原因。

必须保留 query/download future 及相关 shared_ptr，直到消费者已完成使用。取消、超时后的异步持有关系和释放线程尚未验证，不能只在 Python 超时后随意释放原生对象。
