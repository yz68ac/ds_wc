# 不经桌面点击的图片下载：接口与实测

更新：2026-10-26。固定样本为 Linux 微信 4.1.13.26 x86_64，主程序 SHA-256：

```text
2749535f299ba67feb8ef80cab898bb0531fa8f376b16f8a72db706811c84132
```

**已通过一张真实、来源绑定的冷缓存图片验证：不切换会话、不点击图片，调用微信内部下载链路，把 140×210 缩略图变成可解密的 850×1276 清晰缓存。** 没有替换生产下载器，也没有验证微信本体可以脱离 Xvfb。本文函数名称均为研究标签，地址均为 RVA，不是官方稳定 API。

## 1. 本轮成功条件与结果

| 检查 | 实测 |
| --- | --- |
| 调用前 | 仅有 thumbnail，JPEG 140×210，解密后 6417 字节；没有 original/cached 文件 |
| 来源 | 当前账号、目标群、server_id、发送者、图片 MD5 均匹配 |
| 执行环境 | 微信自己的后台协程；普通工作线程不具备所需上下文 |
| 内部结果 | coroutine completion = 1；download future = 1；下载状态整数对 = `[0, 0]` |
| 调用后 | 原绑定路径出现 cached；WXGF 解码为 PNG 850×1276、1193677 字节 |
| 资源清理 | 协程完成、回调引用归零、future/shared_ptr 释放、Frida script 解除 |
| 服务 | 微信原 PID 保持；监听、helper、会话和恢复定时器均正常 |
| 业务状态 | 队列接收游标未改变；没有群发、模型 API 请求或桌面操作 |

这里的 cached 是微信清晰缓存，不承诺等于发送者上传的原文件。只验收了一张图片，没有把它描述成跨版本、断网、撤回、重启、所有图片规格均已稳定支持。

脱敏的可分享证据见 [验证结果 JSON](research/native-image-validation.json)。原始实验记录、脚本、反编译与函数指纹保留在工作区 `archives/reverse-engineering/native-image-20261026/`；真实账号、消息绑定与图片未复制到 Windows 或 Git，本轮专用 tmpfs 绑定已删除。

## 2. 最终通过的调用链

```text
主进程取得当前群原图片的来源证明与缓存绑定
  → 微信原生数据库工作项：按群 ID + server_id 查询
  → future 就绪后读取 optional<核心消息记录>
  → 比对群、消息 ID、发送者、图片 MD5、消息类型
  → 用共享所有权保留核心记录
  → 通过微信自己的协程调度器执行下载启动入口
  → 保留返回的 download future，不阻塞消息主循环
  → future 就绪后读取带类型的结果，核对状态
  → 从原消息绑定缓存重新读、解密、验图
  → 完成后释放所有原生引用和注入代码
```

这条链路不使用 ChatInputView、当前选中聊天、AT-SPI、鼠标坐标或桌面截图。原消息绑定依然是唯一图片来源；函数返回、按钮动作或 CDN 任务创建都不能代替缓存验收。

## 3. 关键入口

| RVA | 作用与边界 |
| --- | --- |
| `0x6517cd0` | 从 UI 消息模型取核心 shared_ptr，再转交下载入口；本轮最终调用未依赖 UI 模型 |
| `0x6517dc0` | 完整消息下载启动入口：out future、核心消息服务、核心消息 shared_ptr、资源规格、来源/优先级、options |
| `0x6247520` | 微信现有协程调度入口；本轮以原生 C 回调适配器接入，验证实际获得协程上下文 |
| `0x6b49960` | 按会话和 server_id 查询；无效输入返回空值，真实分支内部仍可能协程等待，不能直接放进普通 GLib 回调 |
| `0x6baa5a0` | 微信现有数据库查询工作项的执行函数；本轮复用其工作项布局，后台取得来源记录 |
| `0x674bb30` | 数据库工作项调度；普通工作线程本身不等于协程 |
| `0x605f720` | 复制 UI 模型 `+0x238/+0x240` 处的 shared_ptr 并原子加引用；只验证了该固定实现的复制语义 |
| `0x6541270` | 读取有值的消息查询结果；返回 optional 核心记录，present 标记在 `+0x278` |
| `0x6545070` | 下载结果访问器；成功路径读取其返回整数状态对 |
| `0x9abce00` | 读取 future 共享状态 `+0x84`；0 待定、1 有值、2 异常 |
| `0x9abe480` | 通用结果访问，pending 时可能阻塞；不能把它当成无阻塞轮询 |
| `0x6a40dc0` | 创建较下层的图片下载工作对象；创建成功不证明下载已完成 |
| `0x7991290` | 将图片工作对象提交到下载管理器；本轮曾观察到 CDN 创建，但单独此路径没有验收到缓存 |
| `0x8c2e870` | CDN 图片任务创建候选；已在限定目标下载调用栈内观察到创建，不代表文件成功 |

重要类型修正：`0x6b49960` 查询返回的 0x278 字节记录是核心消息记录，不是持有 `+0x238/+0x240` 核心指针的上层 UI 模型，不能把两者混用。本轮把查询 future 的控制块与其内部记录组成别名 shared_ptr，使异步消费者保留真实所有权；没有手动改写既有对象引用计数或伪造 UI 模型。

Ghidra 项目显示地址带 `0x100000` image base；伪 C 中的函数和数据地址需要减去该基址。本文表格和 profile 都已采用实际 RVA。每次 attach 前检查可执行文件路径、进程属主、整文件 SHA-256 和函数字节指纹。

## 4. 为什么“移到后台线程”仍然失败

上层 `0x70e7530` 显式使用协程等待。更下层 `0x6517dc0` 自身没有直接出现同一个 wait 调用，但它的下游仍有服务获取和消息检查，会访问当前协程。

实验分别确认：

1. **无效查询可成功。** server_id 为 0 时返回空 optional，并正确清理；它只覆盖快速返回分支。
2. **真实查询需要正确路径。** 真实分支包含等待，改为复用微信后台数据库工作项，不在主线程调用上层查询包装器。
3. **直接 GLib 下载调用失败。** 异常定位在 `0x9ae3540` 内的 `0x9ae35b2`；这里读取当前协程 TLS 后访问其对象，缺失上下文时产生访问异常。微信进程未退出，探针捕获后清理。
4. **普通原生工作项没有协程上下文。** 最小只读 C 探针在微信自己的普通执行器上运行，检查结果仍为空。
5. **微信原生协程有效。** 通过 `0x6247520` 调度后，上下文存在、完成 promise 就绪、回调引用归零；再运行完整下载入口，最终缓存验收成功。

没有写 TLS、借用别人的协程裸指针、修改微信程序代码或屏蔽校验函数。

中途还验证了较下层的任务工厂：对象与控制块类型匹配，规格 2 的目标是原绑定 cached 路径；提交后目标执行入口、CDN 工厂均被观察到，但 30 秒观察窗口内没有清晰文件。**为什么单独该路径没有完成，尚未确认。** 完整协程路径成功不能反推它一定是缺失收尾、引用提前释放或网络失败，不把这些猜测写成结论。

## 5. 来源绑定、参数和结果

消息服务从已有账号同步缓存定位，避免调用可能等待或延迟创建服务的 getter：

```text
base + 0xacf6710 → kernel
kernel + 0x68    → account
account + 0x28   → 核心服务上下文
  同步缓存：context + 0x00
  异步缓存：context + 0x28
```

该时刻同步缓存 85 项、异步缓存为空；分别唯一匹配消息服务、数据库服务和下载服务。消息服务虚表 RVA 为 `0xa8c4568`，数据库服务为 `0xa8b5090`，下载服务为 `0xa9852a8`。对象地址不可跨进程重启保留。

本轮核心消息字段核对：`+0x0c` 类型为 3，`+0xf8` server_id 匹配，`+0x48` 发送者匹配；经正常会话访问器取得的群 ID 匹配，消息内容中的图片摘要匹配。查询并不把日志或模型提供的消息 ID 当作可信来源。

本次完整下载采用正常调用点已见到的参数组合：资源规格 `2`、来源/优先级候选值 `200`，options 首整型为 `1`，其余两个字符串选项为空。规格 2 的 cached 目标在工厂对象和最终文件中分别核对通过；没有完整映射规格 1/3，也没有把 200 解读为超时时间。

所有结果访问器都先检查 future 有值。Ghidra 曾将带类型访问器误推为 `void`，实际汇编返回 RAX 指针；原型以汇编和调用点交叉核对，不照抄伪 C。

## 6. 原生回调与生命周期

普通 JavaScript 回调不适合承载需要挂起、恢复的原生协程栈。本轮通过已有 Frida CModule 编译极小 C 适配器，按当前 libc++ `std::function<void()>` 的克隆、销毁和调用 ABI 提供原生回调；它不操作微信 UI、不自行查库、不发送消息。

客户端调度句柄在本版本有完成 promise（`+0xa0`）。主线程观察完成状态后释放调度句柄，并确认适配器的全部克隆引用归零，再释放图片下载 future 及源记录。C++ 异步消费者使用微信自己的控制块，缓存、下载对象和回调的所有权都不能随着一次 Python RPC 返回就结束。

即使 Python 等待超时，也不能卸载仍在执行的 C 回调。实验控制器对未完成的原生协程保留进程与注入生命周期；图片下载结果不明确时不循环重提任务。后续 SDK 已加入取消、异常、进程退出、回调晚释放和版本不匹配的合成故障回归，真实部署前仍需验证封装后的进程生命周期。

## 7. 生产接入尚未做什么

接口研究与单样本端到端验证后，已将控制器收敛为独立、默认关闭的 [原生图片 SDK](NATIVE_IMAGE_SDK.md)。包含受约束 helper 请求、来源核对、串行执行、请求去重、取消与排空，以及原绑定缓存验收。没有接入 bot，没有部署到 Linux；线上 `wechat_linux.desktop.image_download` 仍是兼容下载器。

接入生产前仍需要：

- 在应用层接入持久任务与重启恢复；当前图片请求去重是内存态，重启后未知结果不能重放。
- 更新可信 helper 资源部署及服务停止策略，不能用现有 8 秒强停配置运行仍持有 C 回调的图片 worker。
- 覆盖账号切换、进程重启、撤回/过期图片、空结果、慢网络、损坏缓存、其他规格和原生异常。
- 将封装后的 C 适配器、任务完成与引用释放纳入真实故障回归；版本不匹配时继续拒绝执行。
- 通过后再决定何时切换生产、是否保留桌面兼容降级。

无需桌面点击下载图片，仍不意味着微信本体、启动或登录不需要虚拟显示环境。当前 Xvfb 会话保持运行，没有为本实验重启微信或更改认证状态。

现有生产行为见 [清晰缓存下载](IMAGE_DOWNLOAD.md)，整体背景见 [技术报告](WECHAT_RESEARCH_REPORT.md)。
