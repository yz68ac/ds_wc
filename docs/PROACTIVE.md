# 主动接话

2026-10-21 新增。Linux按用户要求开启，默认配置及示例保持关闭，避免新部署未确认就自动发言。实际配置可写 `"proactive": {"enabled": true}`，其余值从默认 JSON 合并；修改配置后重启 `wxbridge-bot.service`。

## 判断和发送

最近300秒至少有10条群成员文字消息，且机器人账号没有发出消息时，才考虑主动接话。按消息实际发送时间、local_id去重；纯图片、表情、语音、系统通知、拍一拍不计入十条。引用文字按一条消息计数。机器人本人发图也会抑制接话。

有新消息时最多每10秒检查一次资格；符合门槛才调用一次模型，同时判断是否适合说话并生成短句。模型可以选择沉默。不适合插入的对话、已经结束的话题、只有无意义刷屏或缺少依据时不硬接。没有新消息不再次判断；一次判断后至少间隔60秒、至少新增3条文字才重新考虑。刚上线时记录当前游标，只有之后有新消息才考虑，避免上线就重放旧聊天。

使用现有模型及人格、已有记忆，主动判断关闭思考，最多256 tokens，20秒总请求时限；主回复的high不变。主动句子约10字、最多30字，纯文本一条，不搜索、不猜图片、不公开判断理由。没有调用模型的内部推理作为正文，也不另发“我在想”等提示。

主动生成在独立工作进程进行，计入原有最多两个有效API任务的并发预算。真实@任务优先，抢占尚在生成或尚未提交的主动句子。主动消息进入现有SQLite队列，使用相同目标群、草稿保护和数据库发出确认。发送前再次检查最近消息；机器人已发言、有@任务、超过60秒有效期，或判断期间新增3条文字，则取消未提交的主动句子。三条新文字只是保守失效条件，不代表程序能准确判断话题是否切换。

已存在发送意图的任务必须先核对，不能因来了@就忽略不确定的提交结果。进程重启后未提交的短句重新校验，已提交的先核对数据库，禁止盲目重发；判断水位持久在内存队列，避免相同窗口反复请求。主机重启后队列仍按原设计清空，重新等待上线后的新消息。主动消息确认后不触发额外记忆整理，后台学习仍沿用真实互动的原有规则。

## 配置

| proactive下的字段 | 默认 | 说明 |
| --- | --- | --- |
| enabled | false | Linux实际配置已按用户要求开启 |
| window_seconds | 300 | 活跃及机器人无发言的滚动窗口 |
| min_messages | 10 | 群成员文字条数下限，包含第10条 |
| check_interval_seconds | 10 | 有新消息时的资格检查最短间隔 |
| evaluation_interval_seconds | 60 | 两次模型判断的最短间隔 |
| min_new_messages | 3 | 再次判断所需新文字数；也是旧主动短句失效门槛 |
| reply_ttl_seconds | 60 | 判断结果有效期，也限制最近一次聊天的年龄 |
| timeout_seconds | 20 | 轻量判断的总请求时限 |
| max_reply_chars | 30 | 主动短句的硬上限，过长就放弃，避免硬截断 |

`queue-status` 和 live-status.json 的 proactive 字段只显示判断水位、次数、条数、阶段和错误类别，不显示聊天、草稿、提示词、成员ID或内部推理。常见outcome为waiting_new_messages、below_threshold_or_bot_spoke、evaluating、silent、queued、foreground_or_disabled、context_changed、expired、error。队列任务增加trigger_kind=proactive以区分主动句子。

## 轮询性能

2026-10-21上线前空闲15秒采样：监听主进程约单核CPU的1.4%、RSS27.12MiB，物理读写增量0MiB、逻辑读取3.427MiB。这只代表短时间空闲采样，不含微信客户端、API/UI子进程和活跃群聊峰值。0.5秒是调度休眠上限，每轮两次补读，空闲约每秒四组消息查询；实际周期还要加查询耗时。

数据库和WAL时间戳未变时复用私有内存盘的解密副本，不会每半秒重解密整库。有变化时需刷新，完整库变化触发解密，WAL变化触发WAL校验和应用；现有WAL处理并非恒定成本的仅最新一条读取。主动功能不按0.5秒调用模型，额外资格查询有新消息和10秒节流，API请求另受60秒与新消息门槛限制。
